### Objective

Build a multi-homed router with one interface in each of three isolated segments (USERS, SERVERS, DMZ) plus a NAT uplink, deploy a client in USERS, and **verify the behaviour with IP forwarding disabled** before enabling it.

The objective was not full connectivity. It was to observe the intermediate state in which the router replies but does not route, because that contrast is what makes visible exactly what `ip_forward` contributes.

### Steps performed

1. Cloned `debian-base` → `lab-router`, regenerating all MAC addresses.
2. Four adapters on `lab-router`: NAT plus three internal networks (`intnet-users`, `intnet-servers`, `intnet-dmz`).
3. Identified the adapter → interface mapping with `ip -br link` before configuring anything.
4. Determined that Debian 13 uses NetworkManager rather than `ifupdown`. Configuration via `nmcli`, not `/etc/network/interfaces`.
5. Three static profiles with no gateway (`seg-users`, `seg-servers`, `seg-dmz`).
6. Cloned → `ws-user01`, single adapter on `intnet-users`, profile `ws-lan` with a gateway.
7. Removed the orphaned `Wired connection 1` profile inherited from cloning.
8. Verified with `ip -br addr`, `ip route`, `sysctl net.ipv4.ip_forward` and three pings.
9. ARP capture with `tcpdump` to confirm layer 2 resolution.
10. Snapshots `sesion01-segmentos-ok` and `sesion01-cliente-ok` taken with the VMs powered off.

### Result

All three segments operational. Ping behaviour as predicted: `10.10.10.1` and `10.10.20.1` reply, `8.8.8.8` fails. `ip_forward = 0` confirmed.

### Failures and diagnosis

#### Failure 1 — Pings failing with the router VM powered off

**Symptom:** from `ws-user01`, `ping 10.10.10.1` returned `Destination Host Unreachable`. It looked like a network configuration error.

**Actual cause:** `lab-router` was powered off. All three pings were fired at a segment with nobody on the other end.

**Diagnosis:** the message was the clue. `Destination Host Unreachable` on the local network is generated by **the source machine**, not by a remote router: it means it broadcast an ARP request asking who holds `10.10.10.1` and nobody answered. An IP misconfiguration would have produced a different symptom.

**Takeaway:** before debugging configuration, verify the running state of every machine involved. And read the error message literally: *who* emits it narrows the problem as much as *what* it says. The distinction between a loud local failure and a silent remote drop is pure diagnosis, and it applies identically in a SOC investigating why two systems cannot communicate.

#### Failure 2 — Host / guest context confusion with `VBoxManage`

**Symptom:** `VBoxManage` not found when attempting to run it inside the Debian VM.

**Cause:** `VBoxManage` is the **hypervisor's** management tool. It lives on the Windows host (`C:\Program Files\Oracle\VirtualBox`), not on the virtualised machine. The VM has no control — and should have none — over the hypervisor running it.

**Takeaway:** maintain explicit awareness of which machine you are typing on. Once there are several VMs and several SSH sessions open, this stops being trivial. Measure adopted: per-host differentiated prompts and a `hostname` check whenever in doubt.

#### Failure 3 — Typos in long commands (`coonection`, `metthod`)

**Symptom:** `argument 'coonection' not understood`, and the equivalent with `ipv4.metthod`.

**Cause:** manually transcribing long `nmcli` commands into the VirtualBox graphical console, with no clipboard available.

**Takeaway:** `nmcli` accepts abbreviations (`nmcli con add`, `nmcli c s`), which reduces the error surface. Measure adopted: work over SSH from the macOS laptop instead of the VirtualBox console, or enable bidirectional clipboard. A typo is not a comprehension failure, but it consumes real time and is eliminated with the right tooling.

### Concept consolidated

A router with an interface in each network **replies** from all of its addresses without needing any forwarding at all, because each one is a local address of its own. `ip_forward` does not control whether the router speaks; it controls whether it **relays conversations between others**. These are two distinct capabilities, and conflating them leads to misdiagnosis.

Operational corollary: a device replying to ping on a network does not imply it is routing traffic toward that network.
