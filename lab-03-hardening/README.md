# Lab 03 — Router hardening

Continuation of [`lab-02-nat-firewall`](../lab-02-nat-firewall/). That lab filtered traffic passing *through* the router but left traffic addressed *to* it unrestricted, and the router itself was a full GNOME desktop installation running twenty-five services.

This lab closes that gap: default-deny on the `input` chain, sshd bound only to internal interfaces, persistent logging, and the removal of everything the machine does not need to be a router.

## What it demonstrates

| Capability | Mechanism |
|---|---|
| Traffic to the router is filtered | `input` chain with `policy drop` and explicit allow rules |
| SSH is unreachable from the external leg | `ListenAddress` on internal addresses only |
| Logs survive a reboot | `/var/log/journal` with `SystemMaxUse=200M` |
| Attack surface reduced | Desktop environment purged, 11 unnecessary services removed |

## Input chain policy

    chain input {
        type filter hook input priority filter; policy drop;
        iifname "lo" counter accept
        ct state established,related counter accept
        iifname { "enp0s8", "enp0s9", "enp0s10" } tcp dport 22 counter accept
        iifname { "enp0s8", "enp0s9", "enp0s10" } ip protocol icmp counter accept
        counter log prefix "INPUT-DROP: " drop
    }

Loopback first, because a system talks to itself constantly and blocking that breaks services in ways that are hard to trace. Then established connections — the replies to traffic the router itself initiates: DNS, NTP, `apt`. Then SSH and ICMP, permitted only from the three internal segments. Everything else is logged and dropped.

The chain was created with `policy accept`, populated, verified, and only then switched to `drop`. Building it the other way locks you out the moment the chain exists.

### input and forward are separate paths

`ping 10.10.20.1` from USERS succeeds even with a full `forward` deny policy, because that address belongs to the router and the packet never crosses between interfaces. The counters prove it — that ping registers in the `input` chain and in no rule of `forward` at all.

The distinction is visible in the logs. `OUT=` is populated for forwarded traffic and empty for traffic addressed to the router:

    FWD-DROP:   IN=enp0s8 OUT=enp0s9  SRC=10.10.10.10 DST=10.10.20.50 TTL=63
    INPUT-DROP: IN=enp0s8 OUT=        SRC=10.10.10.10 DST=10.10.10.1  TTL=64

TTL differs too: 63 for the forwarded packet, already decremented; 64 for the one that was never routed.

## sshd bound to internal interfaces

    ListenAddress 10.10.10.1
    ListenAddress 10.10.20.1
    ListenAddress 10.10.30.1

The firewall already blocked SSH from the external leg, so this is defence in depth: a service that does not listen where it should not is one layer that does not depend on another layer working. It also closed the `[::]:22` wildcard socket — sshd was listening on IPv6 despite IPv6 being disabled on the interfaces, and the `nftables` rules are IPv4-only.

Before and after, from `ss -tlnp`:

    LISTEN  0  128  0.0.0.0:22     →   LISTEN  0  128  10.10.10.1:22
    LISTEN  0  128  [::]:22            LISTEN  0  128  10.10.20.1:22
                                       LISTEN  0  128  10.10.30.1:22

This change broke sshd on the next boot. See Failure 15 — the service started before NetworkManager had configured the interfaces and could not bind to addresses that did not yet exist. Fixed with a systemd dependency on `network-online.target`.

## Attack surface reduction

The router was a GNOME desktop installation. Enabling logging on the drop rule made that visible: 104 of 110 dropped packets in one boot were mDNS announcements the router was sending to itself on all four interfaces, generated by `cups-browsed` — a service that finds network printers.

    104 PROTO=UDP SPT=5353 DPT=5353     ← mDNS
      4 PROTO=UDP SPT=*    DPT=3702     ← WS-Discovery
      2 PROTO=TCP SPT=48614 DPT=80      ← the actual test

A router announcing itself by multicast across three segments is exposure with no function, and the noise buried the two entries that mattered. Purging the desktop and removing eleven services brought the drop counter from 119 to 0 after a clean boot.

What remains listening, in full:

    tcp LISTEN 10.10.10.1:22  sshd
    tcp LISTEN 10.10.20.1:22  sshd
    tcp LISTEN 10.10.30.1:22  sshd

## Verification

From `ws-user01`, after a clean reboot with no intervention:

| Test | Result |
|---|---|
| `ssh vboxuser@10.10.10.1` | Connects |
| `ping 10.10.10.1` | Replies |
| `ping 8.8.8.8` | Replies, `ttl=62` |
| `nc -zv 10.10.10.1 80` | Timeout, logged |

The timeout rather than `Connection refused` is the expected signature of a `drop`: nothing answers, and the client waits out its timer. A `reject` would confirm the host exists; a `drop` tells a scanner nothing.
